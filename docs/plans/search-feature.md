# 검색 기능 설계 노트

> 가계부에 검색 기능을 도입할 때의 UX 결정 포인트, 현재 스택(SQLite + Rails 8)에서의 최적화 전략, Postgres / Elasticsearch 등 상위 스택으로 점진 확장하는 로드맵을 정리한 문서. **아직 구현 단계 진입 전** 의 사고 정리이며, 작업 시작 시 이 문서를 기반으로 phase 스펙을 쪼갠다.

## 1. 배경 및 목적

- 메인 화면의 "총 자산 카드" 영역에 **검색창**을 배치해 가계부 전반을 검색하는 기능을 추가하고 싶다.
- 단순한 LIKE 검색이 아니라:
  - 한국어 형태소 / 부분 매칭 / 오타 허용
  - 카테고리·설명·금액 범위·태그·태그 설명 등 **다중 필드 검색**
  - 검색 결과를 **달력 UI 위에 시각화** (hit한 날짜 indicator + 항목 highlight)
- 동시에 학습 가치도 살리고 싶다 — Postgres FTS, pg_trgm, 형태소 분석기, Elasticsearch / Meilisearch 등을 단계적으로 경험.
- 단, 가계부의 **현실적 데이터 규모는 작다**(개인 사용자 기준 수만 건 수준). 따라서 **"필요해서"가 아니라 "학습 가치 + 추상화 연습"으로** 상위 스택을 선택해야 한다.

## 2. 검색 UX 결정 포인트

### 2.1 트리거 방식 (debounce vs Enter)

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| Debounce (250~400ms) | 즉각적 피드백, 검색 모드로 자연스럽게 진입 | 매 keystroke마다 쿼리 → DB 부하, 한국어 IME 입력 중 중간 글자로 검색됨 |
| Enter only | 명시적, 부하 적음, IME-safe | 탐색적 검색이 어색함 |
| **하이브리드 (추천)** | 2글자 미만은 무시 + 350ms debounce + IME `compositionend` 이후만 발화 | 구현이 약간 더 복잡 |

가계부는 "검색해서 발견"보다 **"기억나는 항목 찾기"** 가 많으니 하이브리드가 적합. 한국어 IME는 `compositionstart` / `compositionend` 이벤트로 조합 중에는 fire하지 않게 막는 것이 핵심 — Stimulus controller 한 개로 처리 가능.

### 2.2 "검색 모드" 진입의 시각 언어

- 기본 상태의 강한 시그널(오늘 테두리, 선택일 하이라이트)을 **지우지 말고 opacity를 낮춰** 살아있게 둔다 → "원래 모드로 돌아갈 수 있다"는 단서가 됨.
- Hit된 날짜는 **다른 채널**의 시그널을 사용. 오늘 테두리가 색이라면 hit는 *밀도*(작은 dot) 혹은 *배경 채움*으로. 채널이 충돌하면 시선이 분산됨.
- Hit 강도(그날 1건 vs 8건)를 dot 개수나 채도로 표현 — GitHub contribution graph 패턴.
- 오른쪽 리스트의 hit 항목 highlight는 **배경 tint + 매칭된 텍스트 부분만 굵게/색**.
- ⚠ 한국어 형태소 검색 도입 시: 원본 텍스트와 token 위치가 어긋나서 "어디가 매칭됐는지" 시각화가 까다로워짐. 미리 염두에 둘 것.

### 2.3 전체 검색의 문법 vs 필드 분리

| 방식 | 설명 | 평가 |
| --- | --- | --- |
| 단일 검색창 + 자동 필드 추론 | `1000~2000` → 금액 범위, `#베풂` → 태그, 그 외 → 설명+카테고리 | 인지 부담 적음, 파싱 로직 직접 구현 필요 |
| 칩(chip) 기반 필터 빌더 | 입력 → 드롭다운으로 칩 추가 (Linear / Notion 방식) | 가장 강력, 구현 무겁 |
| 고급 검색 토글 | 기본은 단순 텍스트, "고급" 클릭 시 필드별 입력 | 가장 단순 |

가계부 도메인 권장: **단일 검색창 + 칩 자동완성 일부**.
- `>5000`, `<10000`, `5000~10000` 같은 prefix 문법은 직관적
- `#태그`도 자연스러움
- 카테고리는 종류가 적으니 칩 자동완성이 가벼움

## 3. 현재 스택(SQLite + Rails 8)에서의 최적화 전략

SQLite는 생각보다 강력하다. 단계적으로 깎아내려 간다.

### Tier 0 — `LIKE`의 한계 인식

- `LIKE '%foo%'`는 인덱스를 못 타고 풀스캔.
- 596건은 무시 가능, 5만 건 넘어가면 체감.
- 한국어는 `LOWER()`도 의미 없고, 부분 매칭은 되지만 오타("카페" vs "까페")는 못 잡음.

### Tier 1 — SQLite FTS5 (외부 의존성 0)

- SQLite 내장 풀텍스트 검색 가상 테이블. Rails와 잘 어울림.
- Rails 모델(`Transaction`, `Tag`, `Category`)의 검색 대상 텍스트를 `transactions_fts` 가상 테이블에 인덱싱.
- 트리거 또는 `after_save` 콜백으로 동기화.
- **Tokenizer 선택이 핵심**:
  - 기본 `unicode61`은 공백 분절 → "카페에서" → "카페" 매칭 안 됨
  - **`tokenize='trigram'`** (SQLite 3.34+) → 한글 부분 매칭 가능. 형태소 분석은 아니지만 **실용적으로 충분**.
- 금액 범위·날짜·카테고리·태그는 FTS와 함께 일반 SQL `WHERE`로 결합 (`MATCH`와 `JOIN` 같이 사용 가능).

**얻는 것**: 인덱스 기반 검색 + 부분 매칭 + 다중 필드 결합. **5만~10만 건까지 무리 없음**.

### Tier 2 — 검색 인덱스 테이블 정규화

- 검색 도메인 전용 모델 `SearchableEntry`(transaction을 평면화한 검색 전용 행)를 둔다.
- Transaction 저장 시 카테고리명, 태그명, 태그 설명까지 한 행에 합쳐 비정규화.
- JOIN 없이 한 번에 검색 → 성능 ↑.
- Rails에서는 `after_commit` 콜백 또는 Solid Queue job으로 처리.

### Tier 3 — 쿼리 파서 분리 ⭐ (핵심 추상화)

- `SearchQueryParser` 같은 PORO를 만들어 입력을 분해.
  - 예: `"카페 >5000 #베풂"` → `{ text: "카페", amount_gt: 5000, tag: "베풂" }`
- 컨트롤러는 파싱 결과를 받아 `SearchableEntry.search(parsed)` 호출.
- 백엔드를 PG / ES로 바꿔도 **파서는 재사용**됨.
- → **마이그레이션 cost를 낮추는 핵심 설계**.

### Tier 4 — 결과 캐싱

- 같은 검색어가 자주 들어오면 Solid Cache로 캐싱.
- 가계부는 read-heavy라 hit-rate가 의외로 높음.
- Cache key: `user_id + query_hash + max(transactions.updated_at)`.

여기까지 가면 **SQLite로도 수십만 건까지** 학습용으로 충분하다.

## 4. Postgres 전환 시의 가치

### 4.1 언제 가치가 있는가

SQLite FTS5 trigram이 잡지 못하는 케이스가 도메인적으로 중요해질 때.

- "사다" / "샀다" / "구매"를 동의어로 묶고 싶을 때
- "카페" 검색에 "까페" 같은 오타도 잡고 싶을 때
- 진짜 한국어 형태소 분석(조사 분리, 어간 추출)이 필요할 때

### 4.2 Postgres에서 쓸 수 있는 기술

| 기술 | 설명 | 한국어 적합도 |
| --- | --- | --- |
| `tsvector` + `tsquery` | 내장 FTS. 영어 강력 | 한국어 dictionary 부재로 기본 약함 |
| **`pg_trgm`** | trigram 유사도 (`%` 연산자, `similarity()`) | ⭐ 한국어에 잘 맞음. 오타 허용, 부분일치, GIN 인덱스 가능 |
| **`pg_bigm`** | bigram 인덱스 — `pg_trgm`보다 한국어 정확도 ↑ | ⭐⭐ 일본·한국 커뮤니티에서 검증됨 |
| **`mecab-ko` + `pg_jieba` 류** | 형태소 기반 `tsvector` | ⭐⭐⭐ 진짜 형태소 검색. 설치/관리 비용 ↑ |
| `unaccent` + 사용자 사전 | 동의어 매핑 | 도메인 단어 사전이 있어야 빛남 |

### 4.3 실용적 결론

- 가계부는 사용자별 텍스트가 짧고(설명 한 줄, 태그) 어휘도 한정적 → **`pg_trgm` + GIN 인덱스로도 90% 만족**.
- 형태소까지 가는 건 **학습 가치는 크지만 ROI는 작음**. 학습 목적이라면 충분히 의미 있음.

### 4.4 비용

- SQLite의 "DB가 파일 하나"라는 운영 단순함을 잃는다.
- 현재 Solid Queue / Cache / Cable이 SQLite 위에 깔려 있으므로, PG로 가면 그 셋도 같이 옮겨야 함(PG에서도 모두 동작은 함).

## 5. Elasticsearch / OpenSearch — 정말 필요할 때

### 5.1 언제 가치가 있는가

다음 중 둘 이상이면 고려.

- 데이터가 단일 user 기준 수십만 건 이상
- 검색 facet (카테고리별 개수 + 금액 합계 + 월별 분포를 검색 결과에 함께 표시)
- Fuzzy / synonym / autocomplete 모두 동시 필요
- Multi-tenant + 글로벌 통계도 빠르게

### 5.2 가계부 현실 점검

- 한 사용자가 평생 모아도 수만 건 수준.
- user별 데이터 격리 → **단일 사용자의 검색 부하는 항상 작음**.
- ES의 진가는 "큰 코퍼스에서 작은 결과"인데, 가계부는 "작은 코퍼스에서 작은 결과" → ES가 가진 카드 대부분이 안 쓰임.

### 5.3 그럼에도 학습으로 해볼 가치

- 검색 자체보다 **"분석 + 검색"의 결합**으로 접근하면 의미가 큼.
- 예: "지난 1년간 '카페' 관련 지출의 월별 추이 + 평균 + 다른 카테고리와의 비교"를 한 쿼리로.
- ES의 aggregation이 빛나는 영역이고 가계부 도메인에 잘 맞음.

### 5.4 대안: Meilisearch / Typesense

- ES보다 운영이 가볍고, 한국어 처리도 최근 많이 좋아짐.
- 가계부 규모엔 오히려 더 어울림.
- **ES**는 학습 가치 ↑, **Meilisearch**는 실용 가치 ↑.

## 6. 점진적 로드맵

### Phase A — 지금 (학습 + 충분한 성능)

1. 검색 UX 결정 (하이브리드 debounce, IME-safe, hit 시각화)
2. `SearchQueryParser` PORO 도입 — **백엔드 추상화 layer**
3. SQLite FTS5 + trigram tokenizer
4. 비정규화된 `searchable_entries` 테이블 + Solid Queue로 동기화
5. 결과 캐싱

### Phase B — Postgres 전환 (운영 부담 감수할 가치가 생겼을 때)

1. Solid Queue / Cache / Cable을 PG로 이전
2. `pg_trgm` + GIN 인덱스로 시작
3. 같은 `SearchQueryParser` 재사용, repository만 교체
4. (선택) `pg_bigm` 또는 `mecab-ko` 도전 — 학습 목적

### Phase C — 외부 검색 엔진 (도메인 요구가 바뀌었을 때)

1. Meilisearch부터 도입 (운영 가볍고 한국어 적당히 됨)
2. 또는 ES로 가서 aggregation까지 활용 — 통계 페이지를 ES로 재구성하면 학습 가치 큼
3. PG는 source of truth, 검색엔진은 read-only 인덱스. 동기화는 Solid Queue로

### 핵심 통찰

어느 phase든 **`SearchQueryParser` + 검색 repository 인터페이스**가 추상화 경계다. 이걸 Phase A에서 잘 만들어 두면 B/C 전환이 "구현체 교체"로 끝나고, 못 만들어 두면 컨트롤러까지 다 뜯어야 한다.

## 7. 배포 시 데이터 규모 시나리오 (현실 점검)

| 사용자 | 사용자당 트랜잭션 | 총 행 수 | 권장 스택 |
| --- | --- | --- | --- |
| 1 (본인) | ~10,000 / 년 | ~10K~100K | **SQLite FTS5로 끝.** 평생 충분 |
| 10~100 | ~10K / 년 | ~100K~10M | SQLite도 가능, PG가 편함 |
| 1,000+ | ~10K / 년 | 10M+ | PG + `pg_trgm`. ES는 검색보단 분석용 |

가계부의 본질상 multi-user SaaS가 아니라면 SQLite 한계를 만날 일이 거의 없다. 따라서 **"배포 대비"보다 "학습 가치"** 를 기준으로 phase B/C 진입 여부를 정하는 게 정직하다.

## 8. 요약 한 줄

> 지금은 **SQLite FTS5 trigram + 비정규화 테이블 + 쿼리 파서 추상화**로 끝까지 깎고, Postgres는 형태소 검색 학습 욕구 + 운영 부담 감수 의지가 생겼을 때, ES / Meilisearch는 *검색* 보다 *aggregation/분석*을 같이 가져가고 싶을 때 도입한다. 추상화 경계를 Phase A에서 잘 그어두는 것이 마이그레이션 cost를 결정한다.
